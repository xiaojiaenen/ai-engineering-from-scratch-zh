# 百万Token上下文的长视频理解

> 一段1小时、4K分辨率、24 FPS的视频，经分块和嵌入处理后，会产生约6000万token。一段2小时的播客转录文本约为30,000 token。一部完整的蓝光电影，即使采用激进的池化压缩，也有数十万token。Google的Gemini 1.5（2024年3月）开启了这一时代，它支持1000万token的上下文，能在长达数小时视频中可靠地执行"干草堆找针"式的回忆。LWM（Liu等人，2024年2月）展示了环形注意力（ring attention）的扩展路径。LongVILA和Video-XL进一步放大了视频摄入规模。VideoAgent则用代理式检索替代了原始上下文。每种方案在计算量、召回率和工程复杂度上各有取舍。本课将它们并排解读。

**类型：** 构建
**语言：** Python（标准库、干草堆找针模拟器 + 代理检索路由器）
**前置知识：** 阶段12 · 17（视频时序token）
**时间：** 约180分钟

## 学习目标

- 计算不同FPS和池化策略下长格式视频的视觉token总量。
- 解释三种扩展路径：暴力上下文（Gemini 1.5）、环形注意力（LWM）、token压缩（LongVILA / Video-XL）。
- 对比原始上下文视频VLM与代理检索视频VLM（VideoAgent）在准确率和延迟上的表现。
- 为一段30分钟视频设计干草堆找针测试，并在指定分钟数测量召回率。

## 问题所在

在384原始分辨率下，Qwen2.5-VL尺寸的单帧分块约为729个token。经过3x3池化后，每帧变为81个token。一段1 FPS、30分钟的片段 = 1800帧 = 145,800个token。这在2025年开源VLM中可行，但已接近上限。若提升至2 FPS，则需291,600个token——只有最大上下文模型才能容纳。

一段2小时、1 FPS的电影达到58.3万token。超出了大多数2026年开源模型的承载范围；需要Gemini 2.5 Pro，或更激进地池化。

出现了三种扩展路径。

## 概念解析

### 路径1：暴力上下文（Gemini 1.5、Claude Opus）

用硬件硬扛。将上下文扩展到数百万token，在一次前向传播中处理所有内容。

Gemini 1.5 Pro首发时支持1M token；Gemini 1.5 Ultra达10M；2026年的Gemini 2.5 Pro能可靠处理数小时视频。论文（arXiv:2403.05530）记录了在高达约950万token时，干草堆找针召回率高达99.7%。

工程实现：自定义注意力实现，包含内存层次结构（局部 + 全局 + 稀疏）以及用于长上下文效率的MoE专家路由。未公开完整细节。非开源。

### 路径2：环形注意力（LWM、LongVILA）

环形注意力将长序列分布到多个设备上，每个设备持有一段分块。对完整序列的注意力计算通过每个设备按环形模式将分块发送给下一设备、计算局部注意力并聚合来实现。

LWM（Liu等人，2024）以此方式训练了1M token上下文模型。训练计算量随上下文线性扩展，而非二次增长——注意力的二次开销被分摊到环形各设备上。

LongVILA（arXiv:2408.10188）将该模式适配到VLM。1400帧视频、每帧192个token = 268k上下文，在8路并行下使用环形注意力训练。

### 路径3：Token压缩（Video-XL、LongVA）

比暴力上下文更经济：在LLM看到序列之前就进行激进压缩。

Video-XL（arXiv:2409.14485）使用视觉摘要token：每段N帧视频生成单个"摘要"token，该token对N帧进行注意力计算。推理时，LLM每段仅看到一个摘要token，大幅缩减上下文。

LongVA通过"长上下文迁移"技术将LLM上下文从200k扩展到2M。先在长上下文文本上训练，再通过共享表示迁移到长上下文视频。

Token压缩牺牲了对具体时间戳的精确召回以换取可扩展性。模型知道大体发生了什么，但有时会错过精确帧。

### 路径4：代理检索（VideoAgent）

不将整个视频喂给LLM。而是将视频视为数据库，用LLM进行查询。

VideoAgent（arXiv:2403.10517）：

1. LLM读取问题。
2. LLM调用检索工具请求相关片段（"显示有猫的片段"）。
3. 工具返回匹配的片段时间戳。
4. LLM通过VLM读取这些片段。
5. LLM组合答案或发起后续查询。

这是将LLM-as-agent模式应用于长视频的典型做法。推理成本更低（仅编码相关片段），但工程难度更高（检索质量成为瓶颈）。

### 干草堆找针基准

标准长上下文测试：在视频中随机位置插入唯一的视觉或文本标记，然后提出需要回忆该标记的查询。

指标：在不同视频长度和标记位置下的Recall@k。

Gemini 2.5 Pro在长达90分钟的视频中召回率>99%。开源72B模型（Qwen2.5-VL-72B、InternVL3-78B）在30分钟时得分约85-90%，超过60分钟后性能下降。

VideoAgent在2小时以上的视频中可以匹配甚至超越原始上下文模型，前提是检索工具足够好。

### 如何选型

对于15分钟片段、前沿准确率：开源72B + 原生上下文通常够用。选Qwen2.5-VL-72B。

对于30分钟到1小时内容：开源选LongVILA或Video-XL；闭源选Gemini 2.5 Pro。质量门槛很关键——前沿能力封闭在商业模型中。

对于2小时以上内容：VideoAgent或类似检索模式。或者，先总结为较小片段再喂入分层摘要。

### 2026年生产实践模式

实际上，生产级长视频管线是混合架构：

1. 对整个视频运行动态FPS采样 + 激进池化（得到100k token的全局表示）。
2. 传入72B VLM生成全局摘要。
3. 若用户询问细节，则基于摘要索引运行代理检索。

这结合了暴力上下文的全局理解与检索的局部细节。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------------|------------------------|
| Brute context | "就是更多token" | 将LLM上下文扩展到数百万token；一次性处理所有内容 |
| Ring attention | "LWM式并行" | 分布式注意力模式，每个设备持有一段并按环旋转 |
| Token compression | "摘要token" | 在LLM之前通过学习型压缩器减少每片段token数 |
| Needle-in-haystack | "NIH测试" | 在随机位置插入唯一标记，测试时要求模型回忆 |
| Agentic retrieval | "LLM作为查询规划器" | LLM调用检索工具获取相关片段，通过VLM读取，组合答案 |
| VideoAgent | "视频检索模式" | 典型代理检索设计：问题 → 工具 → 片段 → 答案 |
