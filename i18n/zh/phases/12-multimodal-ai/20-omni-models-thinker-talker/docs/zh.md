# Omni 模型：Qwen2.5-Omni 与思考者-表达者分离架构

> GPT-4o 在 2024 年 5 月的产品演示之所以具有颠覆性，并非因为底层模型本身，而是因为产品形态——一个语音界面，用户可以说话，模型能看到摄像头所见的画面，并在不到 250ms 的时间内回应。开源生态在接下来的 2024 和 2025 年全力追赶这一产品形态。Qwen2.5-Omni（2025 年 3 月）是参考开源设计：一个思考者（大型文本生成 Transformer）加上一个表达者（并行语音生成 Transformer），通过流式语音 token 连接。Mini-Omni 简化了这一架构，Moshi 匹配了其延迟，GLM-4-Voice 将其扩展至中文。本课阅读思考者-表达者架构以及使流式实时对话成为可能的延迟预算。

**类型：** 构建
**语言：** Python（标准库、流式流水线延迟模拟器 + VAD 循环）
**前置条件：** Phase 12 · 19（音频 LLM）、Phase 12 · 16（any-to-any）
**时间：** ~180 分钟

## 学习目标

- 将推理流水线拆分为思考者（文本推理）和表达者（语音合成），并解释为何并行流式处理可行。
- 逐组件计算对话交互的首个音频字节时间（TTFAB）预算。
- 描述 TMRoPE 在思考者内对视觉、音频和文本的时间对齐位置编码。
- 说出三种实时对话模式：半双工、交替发言、全双工。

## 问题

一个实时语音助手需要在极短的时间内完成大量工作：

1. 听。实时语音分词，语音活动检测（VAD），判断用户何时说完。
2. 可选地看。摄像头输入以 2-4 FPS 的速度流式传输到思考者，与音频同时处理。
3. 思考。基于对话历史生成回复。
4. 说。合成语音 token，解码为波形，流式传输到用户扬声器。

每一步都会增加延迟。"对话感"要求总往返时间 < 500ms——低于这个阈值，用户就不会注意到延迟。GPT-4o 声称约 250ms，Moshi 约 160ms，Qwen2.5-Omni 约 350-500ms。

每个组件都需要流式处理。不能是"全部批处理后再解码"。

## 概念

### 思考者与表达者

Qwen2.5-Omni 的分解：

- 思考者：7B-80B 文本生成 Transformer。消费交错的文本 + 图像 + 音频 token，输出代表"要说些什么"的文本 token。
- 表达者：更小的语音生成 Transformer（200M-1B）。消费思考者的文本输出 token 及近期语音上下文 token，输出离散语音 token（residual-VQ 索引）。
- 语音解码器：流式波形解码器（SNAC、MoVQGAN 系列），将语音 token 实时转换为音频采样。

这种分离很关键。思考者必须足够大才能实现良好推理。表达者可以更小，因为它的任务很局部——将文本转为语音 token。更大的表达者并不会更有表现力；它只会更慢。

并行运行：

1. 思考者发出文本 token t_i。
2. 表达者消费 t_i（通过流式传输）并发出语音 token s_i, s_{i+1}, ..., s_{i+k}。
3. 语音解码器消费到来的语音 token 并发出音频采样。
4. 当思考者到达文本 token t_{i+3} 时，表达者已经为 t_0..t_{i+2} 流式传输了音频。

### TMRoPE——时间对齐的多模态位置编码

思考者需要整合图像帧（以约 4 FPS 到达）、音频帧（以约 50 帧/秒到达）和对话历史中的文本。朴素序列顺序（所有图像、然后所有音频、然后文本）会丢失时间对齐。

TMRoPE 为每个 token 分配绝对时间戳。视觉 token 在 t=2.3s，音频 token 在 t=2.32s，用户"停止"的文本 token 在 t=2.35s。RoPE 按时间戳旋转注意力；模型将它们视为时间上并发。

这是让"他一边挥手一边说你好"成立的基础设施——模型在同一概念时刻看到视频帧和音频。

### 流式语音合成

语音 token 必须流式传输。Mini-Omni（Xie & Wu，2024）引入了"语言模型可以在流式处理中边听边说边思考"：思考者输出 token 和表达者输出 token 交错在同一条序列中。表达者在思考者确定下一个文本 token 时立即触发，没有批次边界。

Moshi（Défossez 等，2024 年 10 月）是最快的开源实现。单张 A100 上 TTFAB 仅 160ms。架构：一个 7B Transformer，在交替位置上发出文本和语音 token，并通过"内心独白"将思考流与说话流分隔。这本质上是将思考者和表达者融合进一个模型，配合精心设计的训练。

### VAD 与对话切换

语音活动检测运行在输入侧。两种模式：

- 半双工：用户说话，模型倾听。模型说话，用户倾听。通过 VAD 静音检测（~200ms）实现清晰交接。
- 全双工：双方可以同时说话。模型可以附和（"嗯嗯"）或插话。难度高得多。Moshi 支持此模式。

Qwen2.5-Omni 默认支持半双工，通过静音阈值进行交替发言。全双工需要应用层处理。

### Qwen3-Omni（2025 年 11 月）

继任者。Qwen3-80B 思考者、更大的表达者、改进的 TMRoPE-v2。延迟接近 GPT-4o 的 250ms。开放权重。OmniBench 基准与 Gemini 2.0 Live 竞争。

### 生产环境延迟预算

典型流式交互：

- 麦克风 → 语音 token：40-80ms。
- 预填充（提示 + 历史）：7B 约 100-200ms，70B 则多得多。
- 首个思考者文本 token：40ms。
- 表达者处理首个文本 token：20ms。
- 首个语音 token 提交：40ms。
- Residual-VQ 解码：30ms。
- 语音波形解码：50-80ms。

总 TTFAB：7B 约 320-510ms，70B 约 600-900ms。前沿质量通常意味着 70B+；因此存在前沿延迟差距。

### Token 速率计算

在 16kHz 语音、50Hz 基础语音 token 下，每秒输出需要 50 个语音 token。表达者必须发出 ≥50 tok/s 才能跟上。在 H100 上典型 LLM 吞吐 30-80 tok/s 的情况下，小型（200-300M）表达者足够快；7B 表达者则会落后。

这就是为什么存在小型专用表达者模型而非"直接用主模型"的原因。

## 练习

1. 你的目标 TTFAB 是 300ms。在 7B 思考者和 300M 表达者上，写出每个组件的延迟。

2. Qwen2.5-Omni 使用 TMRoPE。描述当用户在 t=1s 开始说话、摄像头在 t=1.2s 捕捉到一个手势时，模型看到了什么。

3. 全双工支持要求模型在倾听时发出音频。提出一种教授此能力的训练数据格式。

4. 阅读 Moshi 论文第 4 节。描述"内心独白"分离方式，以及它为何避免了思考者-表达者分离。

5. 计算吞吐量预算：表达者必须以多快的速度发射 token 才能跟上 16kHz 语音（50 个基础层 token/秒）？

## 关键术语

| 术语 | 人们所说的 | 实际含义 |
|------|-----------|---------|
| 思考者（Thinker） | "推理大脑" | 大型文本生成 Transformer，产出"要说什么" |
| 表达者（Talker） | "语音生成嘴巴" | 小型 Transformer，将思考者的文本转为离散语音 token |
| TTFAB | "延迟预算" | Time-to-first-audio-byte：从用户说话结束到首个音频采样输出 |
| TMRoPE | "时间对齐 RoPE" | 跨视觉、音频、文本使用绝对时间戳的位置编码 |
| 半双工 | "交替发言" | 用户和模型交替；VAD 静音检测用户结束 |
| 全双工 | "同时" | 模型可同时说话和倾听；具备附和能力 |
| 内心独白 | "Moshi 分离" | 单模型设计，思考流和说话流交错 |
