# LLM 的 FinOps — 单位经济与多租户归因

> 传统 FinOps 在 LLM 支出上会失效。成本是 token 交易，而不是资源在线时长。标签无法映射——一次 API 调用是一次交易，而不是一个资产。工程决策（提示词设计、上下文窗口、输出长度）就是财务决策。2026 年的手册在第一页需要记录三个归因维度：按用户（`user_id`）做座位定价与扩张，按任务（`task_id` + `route`）做产品面成本与优先级，按租户（`tenant_id`）做单位经济学与续约。四个 token 层——提示、工具、记忆、响应——用一个桶会隐藏支出。多租户产品的强制阶梯：每租户限流（预期峰值的 2-3 倍，明确的 429 + retry-after）；每日支出上限（合同上限的 1.5-3 倍；触发限流收紧 + 告警）；支出 z-score > 4 时关停开关（自动暂停 + 通知值班）。归因模式：打标签聚合、遥测连接（trace-ID → 计费；最高精度）、抽样外推、基于模型的分配、事件溯源、实时流式。单位指标：每次已解决查询的成本、每次生成工件的成本——而不是 $/M token。回溯性打标签总会遗漏；在请求创建时进行记录。

**语言：** Python（stdlib，带关停开关的玩具成本归因模拟器）

## 学习目标

- 解释为什么传统 FinOps（标签 + 层级）在 LLM 支出上会失效，并列出三个新的归因维度。
- 枚举四个 token 层（提示、工具、记忆、响应），并说明为什么单桶计费会隐藏成本。
- 为多租户产品设计一个强制阶梯（限流 → 支出上限 → 关停开关）。
- 选择一个单位指标（每次已解决查询/工件的成本），而不是 $/M token。

## 问题所在

你的账单显示 $40,000。但你不知道：
- 哪个租户花了这笔钱。
- 哪个产品功能驱动了这笔支出。
- 是否有个别用户在滥用。
- 是否是提示词膨胀、工具调用或记忆放大导致的。

在提供商侧做标签聚合对云资源（EC2、S3）有效，因为标签会传播到明细行。LLM API 调用不会自动打标签——你必须在调用点给 user/task/tenant 打上标记并透传。回溯性归因总会遗漏边缘情况。

## 概念

### 三个归因维度

**按用户**（`user_id`）：谁在产生多少成本。驱动座位定价、扩张对话、识别高功率用户。

**按任务**（`task_id` + `route`）：哪个产品面花费多少。驱动功能优先级排序、砍掉昂贵功能的决策。

**按租户**（`tenant_id`）：哪个客户是盈利的。驱动单位经济学、续约定价、层级阈值。

在第一天调用点同时记录这三个维度。回溯性归因总是更差。

### 四个 token 层

| 层 | 示例 | 典型占比 |
|----|------|---------|
| 提示（Prompt） | 系统 + 用户输入 | 40-60% |
| 工具（Tool） | 工具调用结果回传 | 20-40%（agent 工作负载） |
| 记忆（Memory） | 历史对话 / 检索文档 | 10-30% |
| 响应（Response） | 模型输出 | 10-30% |

将这四层合并到一个桶中会使优化工作盲目。在归因架构中将它们拆分出来。

### 强制阶梯

1. **每租户限流**。预期峰值的 2-3 倍。返回 429 并附带 `Retry-After`。租户感受到摩擦；不会有意外账单。

2. **每租户每日支出上限**。合同上限的 1.5-3 倍。触发条件：收紧限流 + 通知客户成功团队。

3. **支出 z-score > 4 时的关停开关**（相对于租户基线）。自动暂停租户；通知值班；升级至运维 + 客户成功。

### 归因模式

- **打标签聚合**：在元数据 header 上盖章；稍后聚合。简单；粗糙。
- **遥测连接**：通过 trace ID 将追踪与计费关联。精度最高。成熟团队的做法。
- **抽样 + 外推**：抽样 5-10%，然后乘以倍数。对粗略支出的成本效益较好；会遗漏尾部。
- **基于模型的分配**：回归推断成本驱动因素。用于没有标签的遗留数据。
- **事件溯源**：将成本作为流中的事件（Kafka / Kinesis）。实时。
- **实时流式**：仪表板亚秒级更新。

### 每次 X 的成本才是单位指标

$/M token 是供应商的术语。产品指标：

- 每张已解决的工单成本。
- 每篇生成文章的成本。
- 每次成功的 agent 任务成本。
- 每个用户会话分钟成本。

将成本与产品结果挂钩。否则优化是无锚点的。

### 成本归因追踪形状

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

每次调用都发出。存储在数据湖中。按维度聚合。Phase 17 · 13 可观测性栈是存放这里的地方。

### 复合节省栈

栈：缓存 + 批处理 + 路由 + 网关。四项全部启用时：
- 缓存 L2（Phase 17 · 14）：输入便宜约 10 倍。
- 批处理（Phase 17 · 15）：打 5 折。
- 路由至廉价模型（Phase 17 · 16）：成本降低 60%。
- 网关效率（Phase 17 · 19）：冗余 + 重试。

最佳叠加情况：约为 naive 基线的 5-10%。大多数团队只启用了 2-3 个杠杆；少数人叠加了全部四项。

### 你应该记住的数字

- 归因维度：按用户、按任务、按租户。
- 四个 token 层：提示、工具、记忆、响应。
- 关停开关：支出 z-score > 4。
- 单位指标：每次已解决查询的成本，而非 $/M token。
- 叠加优化：约为基线的 5-10% 是可能的。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| 按用户归因 | "用户级成本" | 每次调用都 stamped 的 `user_id` |
| 按任务归因 | "功能成本" | `task_id` + `route` 标识产品面 |
| 按租户归因 | "客户成本" | `tenant_id`；驱动单位经济学 |
| 四个 token 层 | "成本层" | 提示 + 工具 + 记忆 + 响应 |
| 限流 | "429 防护" | 在网关处强制执行的租户级上限 |
| 每日支出上限 | "每日天花板" | 租户范围的预算与告警 |
| 关停开关 | "自动暂停" | 支出 z-score > 4 触发自动暂停 |
| 每次已解决的成本 | "产品单位指标" | 成本与产品结果挂钩，而非 token |
| 遥测连接 | "追踪到计费" | 最高精度的归因模式 |
| 叠加优化 | "缓存+批处理+路由+网关" | 复合节省至基线的约 5-10% |
