# 大模型的影子模式、金丝雀发布与渐进式部署

> 大模型部署结合了软件部署中最难的几个部分：没有单元测试、故障模式分散、信号延迟。部署流程为：（1）影子模式——将生产请求复制到候选模型，记录日志，与生产输出对比，对用户零影响；能发现明显的分布问题，但不构成质量保证；（2）金丝雀发布——流量逐步迁移 10% → 25% → 50% → 75% → 100%，每一步设门控；跟踪延迟分位数、每次请求成本、错误/拒绝率、输出长度分布、用户反馈率；（3）稳定性确认后，对截然不同的备选方案进行 A/B 测试。非确定性是不可约简的——由于 GPU 浮点数非结合性以及批次大小的差异，相同输入的准确率在不同运行间可能有高达 15% 的波动。成本是变量而非常量——一个性能高 20% 的模型可能每次调用成本高出 3 倍。回滚速度至关重要：如果回滚需要重新部署，说明你太慢了。策略存放在配置/标志中；模型存放在注册表并绑定摘要；回滚 = 翻转策略 + 恢复阈值 + 几秒钟内锁定旧模型。

**类型：** 学习
**语言：** Python（标准库，金丝雀推进模拟器玩具代码）
**前置要求：** 第 17 阶段 · 13（可观测性），第 17 阶段 · 21（A/B 测试）
**时间：** 约 60 分钟

## 学习目标

- 区分影子模式（零影响对比）、金丝雀（实时流量渐进）和 A/B 测试（稳定性确认后的对比）。
- 列举五个 LLM 特有的金丝雀指标（延迟、每次请求成本、错误/拒绝、输出长度分布、用户反馈）。
- 解释为什么 LLM 的非确定性（高达 15%）改变了发布中"稳定"的含义。
- 设计一个只需几秒钟（策略翻转）而不是几小时（重新部署）的回滚路径。

## 问题

你发布了一个新模型。离线评估显示准确率提升了 3%。你在生产环境切换了它。24 小时内，成本上升了 40%，用户差评增加了 8%，三张客户工单报告"奇怪的回答"。你回滚了。重新部署花了 3 小时。你的周末毁了。

以上每一件事都是可以避免的。影子模式会在任何用户看到之前捕获那 40% 的成本激增。金丝雀会在 10% 时因差评移动而停止。策略标志回滚只需 30 秒。正是这种纪律填平了"离线评估看起来不错"和"真实用户满意"之间的鸿沟。

## 概念

### 影子模式

候选模型接收与生产相同的请求；输出被记录，但不会返回给用户。对用户零影响。记录：

- 输出内容（与生产对比）。
- Token 数量（成本差值）。
- 延迟。
- 拒绝和错误。

能捕获：成本爆炸、长度回退、明显的拒绝变化、硬错误。**不能**捕获：用户会感知到的质量差异。影子模式是一个冒烟测试，不是质量测试。

### 金丝雀发布

带门控的渐进式流量切换。典型推进路径：1% → 10% → 25% → 50% → 75% → 100%。在每个步骤对 5 个指标设置门控：

1. **延迟分位数** — P50、P95、P99。触发门控：金丝雀 P99 > 基线 1.5 倍。
2. **每次请求成本** — 混合成本。触发门控：高于基线 20% 以上。
3. **错误/拒绝率** — 5xx 加上明确拒绝。触发门控：2 倍基线。
4. **输出长度分布** — 均值 + P99。触发门控：分布性偏移。
5. **用户反馈率** — 差评/工单提交。触发门控：1.5 倍基线。

### 非确定性是新的方差

相同输入产生不相同的输出。原因：

- GPU 浮点数非结合性（浮点数归约顺序因批次而异）。
- 批次大小差异（相同提示在批次 128 和批次 16 中的结果不同）。
- 采样（温度 > 0）。

实测：相同评估集上运行间准确率差异可达 15%。发布中的"稳定"意味着指标在预期方差范围内，而非与基线完全相同。将门控设置在噪声底噪之上。

### 成本是变量

一个高 20% 的模型可能每次调用成本高 3 倍。每次请求成本是五个门控之一。发布一个"更好"但破坏单位经济模型的模型，就是回滚案例。

### 回滚是武器

- 策略标志（功能标志系统）：翻转配置中的百分比；只需几秒。
- 模型锁定（注册表摘要）：锁定的模型不会自动升级。
- 回滚 = 恢复标志 + 将锁定摘要设置为上一个版本。几秒钟，不是几小时。

如果你的技术栈需要重新部署才能回滚，请在开始发布前修复这个问题。

### 工具

**Argo Rollouts** / **Flagger** — Kubernetes 渐进式交付控制器。与 Istio/Linkerd 加权路由集成。

**Istio 加权路由** — 服务网格级别的流量拆分。

**KServe / Seldon Core** — 内置金丝雀功能的模型 Serving。

**功能标志** — LaunchDarkly、Flagsmith、Unleash。策略级翻转，无需重新部署。

### 指标检查频率

金丝雀门控每 5-15 分钟检查一次，取决于流量规模。1% 流量以 10 req/min 的速度给出每个窗口 50-150 个数据点——足够用于延迟但用户反馈有噪声。10% 流量给出约 10 倍的数据量。推进应在每个步骤暂停足够时间以积累足够的样本。

### A/B 测试是可选的

如果新模型截然不同（不同的行为、不同的成本曲线、不同的语调），在金丝雀通过后在 50% 流量上进行 A/B 测试。如果它只是改进版本，金丝雀门控通过后直接推进到 100%。

### 你应该记住的数字

- 金丝雀推进路径：1% → 10% → 25% → 50% → 75% → 100%。
- 非确定性上限：相同输入运行间差异高达 15%。
- 五个金丝雀指标：延迟、成本、错误/拒绝、输出长度、用户反馈。
- 成本门控：高于基线 20% 以上即触发。
- 回滚：几秒钟，不是几小时。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| 影子模式 | "复制到新模型" | 零影响发送至候选模型用于日志记录 |
| 金丝雀 | "渐进式流量" | 带门控的逐步面向用户的发布 |
| 门控 | "发布检查" | 阻止推进的指标阈值 |
| 非确定性 | "LLM 方差" | 不可约简的运行间差异 |
| 策略标志 | "标志翻转回滚" | 配置级回滚，几秒钟不是几小时 |
| 模型锁定 | "注册表摘要" | 对模型版本的不可变引用 |
| Argo Rollouts | "K8s 渐进式" | Kubernetes 原生金丝雀/回滚控制器 |
| KServe | "推理 K8s" | 带有金丝雀原语的模型 Serving |
| Istio 加权 | "网格拆分" | 服务网格流量拆分器 |
