# 工具调用与函数调用

> Toolformer（Schick 等人，2023）开启了自监督工具标注。Berkeley Function Calling Leaderboard V4（Patil 等人，2025）设定了 2026 年的标准：40% 智能体任务、30% 多轮对话、10% 真实用户提示、10% 合成测试、10% 幻觉检测。单轮调用已解决。记忆、动态决策和长程工具链仍未解决。

**类型：** 构建
**语言：** Python（标准库）
**前置知识：** 第 14 阶段 · 01（智能体循环），第 13 阶段 · 01（函数调用深入）
**预计时间：** 约 60 分钟

## 学习目标

- 解释 Toolformer 的自监督训练信号：仅在执行后能降低下一个 token 损失时才保留工具标注。
- 列出 BFCL V4 的五个评估类别及其各自的测量目标。
- 实现一个具备模式验证、参数强制类型转换和执行沙箱的标准库工具注册表。
- 诊断三个 2026 年的开放问题：长程工具链、动态决策和记忆。

## 问题所在

早期的工具调用问的是：模型能否预测正确的函数调用？现代工具调用问的是：模型能否在 40 个步骤中串联工具，携带记忆，在部分可观测环境下运行，从工具失败中恢复，且不 hallucinate 不存在的工具？

Toolformer 确立了基线：模型可以通过自监督学习何时调用工具。BFCL V4 定义了 2026 年的评估目标。两者之间的差距正是生产级智能体所面对的空间。

## 概念解析

### Toolformer（Schick 等人，NeurIPS 2023）

核心思想：让模型在其自身的预训练语料中为候选 API 调用添加标注。对每个候选调用执行它，仅当包含工具结果能降低下一个 token 的损失时才保留该标注。然后在过滤后的语料上微调。

涵盖的工具：计算器、问答系统、搜索引擎、翻译器、日历。自监督信号纯粹关注工具是否有助于预测文本——无需人工标注。

规模效应：工具使用能力在大规模下涌现。小模型受工具标注伤害；大模型从中获益。这就是为什么 2026 年的前沿模型内置了强大的工具使用能力，而大多数 7B 模型需要显式的工具使用微调才能可靠工作。

### Berkeley Function Calling Leaderboard V4（Patil 等人，ICML 2025）

BFCL 是 2026 年的事实标准评估。V4 的组成如下：

- **智能体任务（40%）** — 完整的智能体轨迹：记忆、多轮对话、动态决策。
- **多轮对话（30%）** — 带有工具链的交互式对话。
- **真实提示（10%）** — 用户提交的实际提示（更难分布）。
- **合成测试（10%）** — 合成测试用例。
- **幻觉检测（10%）** — 检测何时不应调用任何工具。

V3 引入了基于状态的评估：在工具序列执行后，检查 API 的实际状态（例如"文件是否已创建？"），而非匹配工具调用的 AST。V4 增加了网页搜索、记忆和格式敏感度类别。

2026 年的关键发现：单轮函数调用已基本解决。失败集中在以下方面：记忆（跨轮次携带上下文）、动态决策（根据先前结果选择工具）、长程链（20 步以上的漂移）以及幻觉检测（在无不合适工具时拒绝调用）。

### 工具模式

每个提供商都有自身的模式。它们在细节上有所不同，但共享相同的形状：

```
name: string
description: string（说明做什么、何时使用）
input_schema: JSON Schema（属性、必填项、类型、枚举）
```

Anthropic 直接使用 `input_schema`。OpenAI 使用 `function.parameters`。两者都接受 JSON Schema。描述至关重要——模型会阅读描述来选择正确的工具。糟糕的工具描述是导致选错工具失败的首要原因。

### 参数验证

不要信任任何工具调用。务必验证：

1. **类型强制转换。** 模型可能返回字符串 "5" 而模式指定为 int。如果无歧义则强制转换；有歧义则拒绝。
2. **枚举验证。** 如果模式规定 `status in {"open", "closed"}` 而模型输出 `"in_progress"`，则以描述性错误拒绝。
3. **必填字段。** 缺少必填字段 → 立即返回结构化错误观测给模型，而非直接崩溃。
4. **格式验证。** 日期、邮箱、URL——使用具体解析器验证，而非正则表达式。

每次验证失败都应返回结构化观测，以便模型可以以正确格式重试。

### 并行工具调用

现代提供商支持在单个助手回合中并行调用多个工具。循环流程如下：

1. 模型发出 3 个具有不同 `tool_use_id` 的工具调用。
2. 运行时执行它们（相互独立时并行执行）。
3. 每个结果作为 `tool_result` 块返回，通过 `tool_use_id` 关联。

工程准则：将关联 ID 视为关键要素。调换它们会导致工具与结果错误路由。

### 沙箱隔离

工具执行是沙箱边界。详见第 09 课。简要说明：每个工具都应指定读写范围、网络访问、超时时间和内存上限。通用的 `run_shell(cmd)` 是危险信号；具体的 `git_status()` 更安全。

## 动手构建

`code/main.py` 实现了一个生产形态的工具注册表：

- JSON Schema 子集验证器（仅使用标准库）。
- 带描述、输入模式、超时时间和执行器的工具注册。
- 参数强制类型转换和枚举验证。
- 带关联 ID 的并行工具分发。
- 结构化字符串形式的错误观测。

运行它：

```
python3 code/main.py
```

日志展示了微型智能体在一个回合内调用三个工具，其中一次故意格式错误的调用被拒绝，并返回模型可操作的结构化错误信息。

## 实际应用

每个提供商都有自己独立的工具模式——Anthropic、OpenAI、Gemini、Bedrock。如果需要跨提供商支持，请使用转换层（OpenAI Agents SDK、Vercel AI SDK、LangChain 工具适配器）。BFCL 是参考基准——如果工具使用是产品的核心功能，请在上线前对你的智能体运行 BFCL 测试。

## 交付产出

`outputs/skill-tool-registry.md` 为给定任务领域生成工具目录、模式和注册表。包含描述质量检查（每个工具的描述是否告诉了模型何时使用该工具？）。

## 练习

1. 添加一个"空操作"工具，让模型能够明确拒绝使用任何其他工具。在类 BFCL 幻觉测试上度量效果。
2. 实现 int 转字符串和 float 转字符串的参数强制转换。强制转换在何处开始掩盖真正的 bug？
3. 添加每个工具的超时时间和熔断器（连续失败 3 次后拒绝该工具 60 秒）。这会如何改变模型的恢复方式？
4. 阅读 BFCL V4 描述。选择一个类别（例如"多轮对话"）并将 10 个示例提示传入你的智能体。报告通过率。
5. 将标准库验证器移植到 Pydantic 或 Zod。Pydantic/Zod 捕获到了玩具实现遗漏了哪些内容？

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| 函数调用 | "工具使用" | 带有验证模式的结构化输出工具调用 |
| Toolformer | "自监督工具标注" | Schick 2023——仅保留能使下一个 token 损失降低的工具调用 |
| BFCL | "Berkeley 函数调用排行榜" | 2026 年基准：40% 智能体任务、30% 多轮对话、10% 真实提示、10% 合成测试、10% 幻觉检测 |
| 工具模式 | "模型的功能签名" | name、description、参数的 JSON Schema |
| tool_use_id | "关联 ID" | 将工具调用与其结果绑定；对并行分发至关重要 |
| 幻觉检测 | "知道何时不调用" | V4 类别：在不适用任何工具时拒绝调用 |
| 参数强制转换 | "字符串转 int 修复" | 针对可预测的模式不匹配的窄范围修复；如有歧义则拒绝 |
| 沙箱隔离 | "工具执行边界" | 每个工具的读写范围、网络、超时、内存上限 |
