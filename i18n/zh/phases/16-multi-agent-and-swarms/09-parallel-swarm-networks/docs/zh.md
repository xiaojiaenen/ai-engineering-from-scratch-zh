# 并行 / 集群 / 网络化架构

> 与主管（Supervisor）模式对比：没有中央决策者。智能体读取共享事件总线，异步领取工作，将结果写回。LangGraph 明确支持用于去中心化、动态环境的“集群架构（Swarm Architecture）”。Matrix（arXiv:2511.21686）将控制流和数据流都表示为通过分布式队列传递的序列化消息，以消除编排器的瓶颈。这是一种明确的权衡：用确定性和可追溯性换取可扩展性。集群架构适合包含大量独立子问题的任务；不适合需要单一连贯计划的任务。

**类型：** 学习 + 构建
**语言：** Python（stdlib、`threading`、`queue`）
**前置知识：** Phase 16 · 05（主管模式）、Phase 16 · 04（基础模型）
**时间：** 约 75 分钟

## 问题

主管模式能扩展到少量工作者。那成百上千呢？主管本身会成为瓶颈：每一个关于“谁做什么”的决策都必须经过一个智能体。一个缓慢的计划步骤就会卡住整个系统。

集群架构颠覆了这种设计。不再是中央计划者分发工作，而是工作者从共享队列中领取工作。“协调”内化于事件总线的语义中。没有编排器；系统可扩展到队列撑不住为止。

## 概念

### 结构

```
                ┌──── 共享队列 ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     工作者  工作者  工作者   工作者
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            结果池
```

没有编排器。每个工作者循环执行：拉取任务、处理、写入结果（并可选地入队后续任务）。

### 集群架构适用的场景

- **大量独立任务。** 爬虫、转换、分类。任务之间相互独立。
- **时长波动的工作。** 如果某些任务耗时 100ms，另一些耗时 10s，集群会自动平衡负载——快速工作者会领取下一个任务。主管必须预先预估时长。
- **吞吐优先于确定性。** 你关心的是总完成时间，而非严格顺序。

### 集群架构失效的场景

- **有序工作流。** 如果第 3 步需要第 2 步的输出，集群可能导致第 3 步在第 2 步完成前就触发。
- **全局计划型任务。** 复杂的研究问题受益于规划器。一群研究员的集群只能产出独立的事实，而非一份连贯的报告。
- **调试。** 没有中央日志且工作异步，复现 Bug 的成本很高。

### Matrix（arXiv:2511.21686）

Matrix 是 2025 年的论文，将集群推向了其自然结论：控制流和数据流都是分布式队列上的序列化消息。没有中央协调器。容错性来自消息持久化。可扩展性是消息代理的问题，而非系统的问题。

贡献在于一种编程模型：多智能体协调变成了“这个智能体订阅了哪个消息主题？”，而不是“主管下一步会选哪个智能体？”。这使得系统看起来像一个发布/订阅事件网格。

### 图框架中的集群

LangGraph 2025 文档明确将“集群架构”描述为多智能体模式之一：智能体是节点，但边形成带环的有向图，任何节点都可以从池中激活。工作者根据条件从可用工作中选取，而非由主管分配。

### 失效模式：饥饿与热点

如果所有工作者都领取最容易完成的任务，长耗时任务将永远不会被选中，直到只剩下它们。这是典型的队列饥饿。

缓解措施：
- 带显式老化机制的优先级队列（随等待时间增加优先级）。
- 工作者专业化：某些工作者只接“长任务”。
- 背压：限制多少快速任务进入队列。

### 基于内容的路由关联

集群与自然契合基于内容的路由（课程 22）。与其使用通用队列，不如为每种消息类型设置一个队列。专家型工作者仅订阅自己的类型。这是可伸缩至数千个智能体的消息总线架构的基础。

## 构建它

`code/main.py` 实现了一个由 4 个工作者线程组成的集群，从共享的 `queue.Queue` 中拉取任务。任务具有不同的持续时间（有的快，有的慢）。演示对比了以下三种方式：

- **顺序基线：** 一个工作者串行处理所有任务。
- **固定分配：** 每个任务预先分配给特定工作者（主管风格）。
- **集群：** 工作者从共享队列中拉取任务。

集群自动平衡负载；固定分配会导致快速工作者在其分配的任务耗时较长时空闲。

运行：

```
python3 code/main.py
```

输出会显示每个工作者的任务数量（集群分布不均但最优）和墙钟时间（实际耗时）。

## 使用它

`outputs/skill-swarm-fit.md` 评估一个任务是否应该使用集群还是主管模式。输入包括：任务独立性、时长方差、顺序要求、调试需求。

## 交付它

检查清单：

- **带老化机制的优先级队列。** 防止长任务饥饿。
- **工作者幂等性。** 如果工作者在运行中途崩溃，任务可能被拉取多次。工作者必须是幂等的。
- **持久化队列。** 生产环境请使用 Kafka、Redis Streams 或数据库支持的队列。`queue.Queue` 仅存在于内存中。
- **按任务的观测性。** 每个任务都有追踪 ID；每个工作者都记录带该 ID 的启动/结束日志。
- **背压。** 如果队列增长速度超过工作者处理速度，请减缓生产者。

## 练习

1. 运行 `code/main.py`。在变量时长负载下，集群比顺序执行快多少？比固定分配快多少？
2. 添加优先级队列变体（使用 `queue.PriorityQueue`）。根据任务的“重要性”字段分配优先级。观察在持续负载下低优先级任务是否会被饥饿。
3. 实现热点检测器：记录当任何工作者处理的任务数是最慢工作者 3 倍时的情况。这说明了什么关于任务时长分布的信息？
4. 阅读 Matrix 论文（arXiv:2511.21686）的摘要和第 3 节。指出 Matrix 接受的一个特定权衡（可扩展性提升）和它放弃的一个特性（可追溯性、确定性）。
5. 将集群演示转换为使用 `(task_type, payload)` 元组的 `queue.Queue`，让工作者仅订阅特定类型。当任务异构时，哪些路由规则是合理的？

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|------------------------|------------------------|
| 集群架构 | “去中心化智能体” | 工作者从共享队列拉取任务；无中央编排器。 |
| 事件总线 | “智能体订阅主题” | 按类型或内容将任务路由至工作者的消息代理。 |
| 饥饿 | “任务永不运行” | 低优先级任务因高优先级工作持续到达而永不被选中。 |
| 热点 | “单个工作者过载” | 负载不均，某个工作者获得了大部分任务。 |
| 背压 | “减缓生产者” | 当队列填满时，向上游发出停止生产的信号机制。 |
| 幂等工作着 | “可安全重跑” | 任务处理两次产生相同结果。因工作者可能在运行中途崩溃，此项必需。 |
| 持久化队列 | “崩溃不丢失” | 由磁盘或副本存储支撑的队列；工作者崩溃时任务不丢失。 |
| Matrix 框架 | “全消息传递集群” | 数据流和控制流均为分布式队列上的序列化消息。 |
