# 共享内存与黑板模式

> 2026 年多智能体系统中并存着两种方法：**消息池**（所有人都能看到所有人的消息，如 AutoGen GroupChat 或 MetaGPT）和**带订阅的黑板**（智能体订阅相关事件，如 Context-Aware MCP 或 Matrix 框架）。两者都是多智能体系统中唯一的有状态部分——这意味着有趣的 bug 都藏在这里。典型的失败模式是**内存中毒**：一个智能体幻觉出一个"事实"，其他智能体将其视为已验证，准确性会以一种比立即崩溃更难调试的方式逐渐衰减。本课从零构建这两种结构，注入中毒攻击，并展示在生产中实际有效的三种缓解手段。

**类型：** 学习 + 构建
**语言：** Python（stdlib，`threading`）
**前置知识：** Phase 16 · 04（原始模型），Phase 16 · 09（并行蜂群网络）
**时间：** ~75 分钟

## 问题

多智能体系统需要一个让智能体共享事实的地方。一个直观的方案是"通过消息传递一切"——但这只是在用额外的复制来重新发明共享状态。另一个方案是"给每个人一个全局日志"——但全局日志会无限增长且极易被污染。第三种方案是"为每个智能体投影一个视图"——可扩展但需要大量的 schema 设计。

当一个智能体产生幻觉并将幻觉写入共享状态时，所有读取该状态的下游智能体都会将该幻觉当作事实采纳。等到人类发现问题时，推理链已经深入五步，而根本原因是最早写入的第三条消息。调试多智能体准确性衰减比调试崩溃更难。

这就是内存中毒。它是 MAST 分类法（Cemri 等人，arXiv:2503.13657）中第二大有文档记录的失败家族，且是结构性的：任何缺乏溯源且没有不可写验证器的共享内存设计，最终都会显现出这一问题。

## 概念

### 两种主要拓扑

**全量消息池。** 每个智能体读取所有消息。AutoGen GroupChat 和 MetaGPT 使用这种方式。简单、透明、可检查，但在超过 ~10 个智能体时无法扩展，因为每个智能体的上下文会被其他智能体的工作填满。

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

**带订阅的黑板。** 智能体声明对主题的兴趣；底层系统只路由相关的消息。CA-MCP（arXiv:2601.11595）和 Matrix 去中心化框架（arXiv:2511.21686）采用这种方式。可扩展性更强，但需要前期的 schema 设计才能让订阅有意义。

```
                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘
```

### 何时哪种方案占优

- **全量池**在智能体数量少（< 10）、异构且对话时间短的场景下占优。当所有人都能看到一切时，推断谁说了什么是微不足道的。
- **黑板**在智能体数量多、角色同质但实例数量庞大（蜂群）且对话长期运行的场景下占优。路由可以节省 token 成本和避免上下文污染。

生产系统通常混合使用：顶部是小规模全量池（规划层），下面是黑板（执行层）。

### 一次内存中毒场景

三个智能体协作完成一个研究任务。Agent A 是检索智能体。Agent B 是摘要智能体。Agent C 是分析智能体。

1. A 抓取了一个页面并向共享状态写入一条消息："该研究报告了 42% 的准确率提升。"
2. 实际抓取的页面写的是"4.2% 提升"。A 幻觉了一个小数点。
3. B 读取共享状态后写入："报告称准确率大幅提升 42%（来源：A）。"
4. C 读取共享状态后写入："建议采纳——42% 的提升具有变革性。"
5. 最终报告引用了一个从未存在过的 42% 数字。

没有智能体崩溃。没有测试失败。系统"正常工作"了。幻觉从单个智能体的上下文通过共享状态渗透到了每个下游智能体的推理中。

### 为什么这是结构性的

如果没有共享状态，智能体 A 的幻觉就只会停留在 A 的上下文中。下游智能体会重新抓取或重新推导，可能发现错误。有了朴素的共享状态，A 的上下文就变成了所有人的上下文，幻觉被洗白成了事实。

问题不在于共享状态本身——而在于**缺乏溯源且缺乏独立验证器的共享状态**。三种缓解手段可以解决这个问题：

1. **每次写入都记录溯源信息。** 共享状态中的每条记录都记录是谁写的、何时写的、基于什么 prompt，以及（如果适用）智能体引用的什么来源。下游智能体根据溯源信息带着怀疑态度进行读取。
2. **版本化写入；视为追加操作。** 修正是一条覆盖旧记录的新条目，而不是原地更新。审计轨迹得以保留。
3. **至少保留一个不能向共享状态写入的智能体。** 一个只读的验证智能体会抽样检查条目、重新抓取来源，并标记不一致之处。因为它不能写入池，所以不会被池中毒。

### 黑板的先例（Hayes-Roth，1985）

黑板模式比 LLM 智能体早出现了四十年。Hayes-Roth（1985，《A Blackboard Architecture for Control》）描述了专门的知識源（Knowledge Sources），它们观察全局黑板、贡献部分解决方案，并触发其他知识源。2026 年的黑板（CA-MCP、Matrix）是同一模式，用 LLM 智能体作为知识源，用 JSON 块作为部分解决方案。旧文献中关于写争用、机会式控制和一致性的解决方案，现代系统正在重新发现。

### 投影 vs 全量视图

纯粹的黑板给每个订阅者相同的投影（主题范围）。更激进的设计是**按智能体投影**：每个智能体获得一个按其角色定制的视图。LangGraph 的状态归约器是 2026 年的典型实现——归约器函数将全局状态折叠成角色特定的切片。

按智能体投影的可扩展性更强，但需要 schema。如果没有，你就得在每个智能体的 prompt 中重建临时的投影逻辑。

### 写争用模式

多个智能体同时写入是一个并发问题，而不仅仅是 LLM 问题。三种模式有效：

- **顺序写入器（单一生产者）。** 所有写入都通过一个协调智能体序列化。简单，但是瓶颈。
- **带版本控制的乐观并发。** 每条记录都有版本号；写入者在版本不匹配时失败并重试。经典数据库技术。
- **主题分区。** 不同的智能体拥有不同的主题。不存在跨主题争用。需要预先设计分区边界。

大多数 2026 年的框架默认使用顺序写入器，因为 LLM 调用足够慢，争用很少发生，而且瓶颈影响不大。

### 不可写验证器

最重要的缓解手段是只读验证器。实现规则：

- 验证器与团队共享状态（读取黑板或消息池）。
- 验证器对共享状态没有写入句柄——只能写入一个独立的验证通道。
- 验证器独立抓取写入中引用的来源。标记分歧。
- 验证器自身的输出路由给人类或一个独立的决策智能体，永远不反馈回池中。

如果没有这种隔离，验证器的输出就会成为池中的新条目，这意味着一个被毒化的池会毒化验证器，验证器又会毒化它的验证结果。

## 构建

`code/main.py` 使用 stdlib Python 实现了两种拓扑，外加一个玩具中毒攻击和三种缓解手段。

- `MessagePool` — 线程安全的追加日志，支持完整读取。
- `Blackboard` — 基于主题的发布/订阅，支持按智能体的订阅。
- `ProvenanceEntry` — 每次写入都记录（写入者、时间戳、prompt_hash、source_uri）。
- `PoisoningScenario` — 运行一个三智能体研究任务，其中智能体 A 幻觉了一个小数点。打印最终报告。
- `Verifier` — 一个只读智能体，重新抓取来源并标记不一致之处。在验证器参与的情况下运行同一场景。

运行：

```
python3 code/main.py
```

预期输出：
- 第 1 次运行（无验证器）：幻觉出的 42% 传播到最终报告中。
- 第 2 次运行（有验证器）：验证器标记出不一致，池被标记为"flagged"，最终报告包含撤回声明。

## 使用

`outputs/skill-memory-auditor.md` 是一个技能，用于审计任意多智能体系统的共享内存设计，检查溯源、版本控制和验证器隔离。在生产部署新的多智能体架构之前运行它。

## 交付

对于任何共享内存设计：

- 每次写入时记录溯源信息：`（写入者，时间戳，prompt_hash，引用的工具调用，source_uri）`。
- 使日志成为追加只写的。修正引用被覆盖条目的新条目。
- 部署至少一个具有独立来源访问权限的只读验证智能体。
- 将验证器输出路由到独立通道，而非反馈回共享池。
- 记录被覆盖写入的比例——上升的比例是幻觉模式的早期证据。

## 练习

1. 运行 `code/main.py`。确认第 1 次运行传播了幻觉，第 2 次运行捕获了它。
2. 添加第二个幻觉：智能体 B 编造了一个数据集大小。验证器应该能同时捕获两者，而不需要对任何一个进行手动调整。
3. 将全量池切换为带主题分区（`prices`、`summaries`、`analyses`）的黑板。主题分区让哪些中毒场景更难实施，又对哪些没有帮助？
4. 阅读 Hayes-Roth（1985，《A Blackboard Architecture for Control》）。找出论文中两个本课未讨论的、2026 年系统可以从中受益的控制模式。
5. 阅读 CA-MCP（arXiv:2601.11595）。将其共享上下文存储映射到 `code/main.py` 中的 `MessagePool` 或 `Blackboard` 类。CA-MCP 在其之上增加了哪些原语？

## 关键术语

| 术语 | 人们所说的 | 实际含义 |
|------|-----------|---------|
| 消息池 | "共享聊天记录" | 每个智能体都读取的追加日志。完全透明，扩展性差。 |
| 黑板 | "共享工作区" | 基于主题的发布/订阅。智能体订阅相关主题。扩展性更强。 |
| 溯源 | "谁写了什么" | 每条写入的元数据：写入者、时间戳、prompt、来源。 |
| 内存中毒 | "幻觉传播" | 一个智能体的错误进入共享状态，下游智能体将其当作事实采纳。 |
| 追加只写 | "无原地更新" | 修正以新条目形式覆盖旧条目。保留审计轨迹。 |
| 不可写验证器 | "独立审计员" | 只读智能体，重新抓取来源并标记不一致之处。 |
| 投影 | "作用域视图" | 从全局状态计算的按智能体视图。LangGraph 归约器是典型案例。 |
| 知识源 | "专家智能体" | Hayes-Roth 在 1985 年中对黑板参与者的称呼。 |
