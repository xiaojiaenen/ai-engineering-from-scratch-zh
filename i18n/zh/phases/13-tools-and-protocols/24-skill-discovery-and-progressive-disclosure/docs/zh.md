# 技能发现与渐进式披露

> 技能在主体加载之前即变得有用。它的名称和描述赢得目录中的一席之地；更深层的文件仅在任务触及它们时才获得上下文。

**类型：** 构建
**语言：** Python（标准库）
**前置知识：** 阶段 13 · 22（智能体技能：可移植契约与运行时边界）
**时间：** 约 105 分钟

## 学习目标

- 构建一个文件系统发现流水线，将作用域、验证、冲突策略和目录发布分离。
- 解释三个披露层级：目录元数据、活跃指令和任务特定资源。
- 设计引用，使智能体能够直接访问所需细节而无需加载整个包。
- 独立预算目录空间和活跃技能上下文。
- 在技能读取自身资源时拒绝路径穿越和符号链接逃逸。

## 问题

你的智能体安装了 200 个技能。在会话启动时加载每个 `SKILL.md`、参考文件、脚本和模板，会让当前任务淹没在不相关的流程中。什么都不加载会迫使用户记住精确的文件系统路径。

通常的折衷方案是目录：向模型展示每个符合条件技能的紧凑身份和路由描述，然后在选中后仅加载完整主体。这就产生了两个新的工程问题。

首先，发现不仅仅是递归文件搜索。技能可以存在于项目、用户、管理员、插件或内置作用域。两个包可以共享一个名称。符号链接可以指向受信任根之外。一个格式错误的包可以占用目录空间或变得无法调用。

其次，渐进式披露可能变成渐进式困惑。如果 `SKILL.md` 说"读取相关指南"而包包含十二个指南，模型就必须猜测。如果每个指南都指向另外三个文件，加载就会变成无界图遍历。

一个好的运行时使发现和披露都成为确定性的。

## 概念

### 发现是一个编译器流水线

将文件系统视为源代码输入。不要直接将原始路径发布给模型。

```figure
skill-discovery-pipeline
```

每个阶段都应产生结构化数据和结构化失败。发现日志应能回答：

- 搜索了哪些根目录？
- 找到了哪些候选项？
- 拒绝了哪些候选项，以及原因？
- 哪个包赢得了冲突？
- 哪些目录条目因预算限制被截断或省略？

没有这些证据，"模型没有使用我的技能"几乎无法诊断。

### 作用域是运行时策略

可移植规范定义了一个技能包，而不是唯一的安装路径或优先级顺序。主机决定在哪里搜索。

通用运行时可能使用以下作用域：

| 作用域 | 示例根目录 | 预期所有者 |
|---|---|---|
| 工作区 | `<repo>/.agents/skills/` | 项目维护者 |
| 用户 | `<user-data>/skills/` | 单个开发者 |
| 管理员 | `<system>/skills/` | 机器或组织策略 |
| 插件 | 已签名的插件包 | 插件发布者和安装者 |
| 内置 | 运行时包 | 运行时供应商 |

截至 2026 年 8 月，Codex 文档记录了从 `$CWD/.agents/skills` 通过祖先目录到仓库根目录的项目发现，以及用户、管理员和内置位置。它支持符号链接的技能目录。重复名称可能同时出现而非合并。这些是 Codex 的行为，不是 `SKILL.md` 的要求；编写适配器时请验证当前的 [Codex 技能文档](https://learn.chatgpt.com/docs/build-skills)。

不要从目录名称发明优先级顺序。将其声明为策略并进行测试。本课实验使用每个 `Scope` 的显式整数排名，使同一候选集合始终以相同方式解析。

### 冲突需要超越 `name` 的身份

两个名为 `release-readiness` 的包可能是合法的。一个可能是工作区覆盖，另一个是用户默认值。因此目录条目至少需要：

```json
{
  "name": "release-readiness",
  "description": "检查此仓库的发布候选版本。",
  "scope": "workspace",
  "source": "/repo/.agents/skills/release-readiness",
  "selected": true
}
```

常见的冲突策略包括：

| 策略 | 优势 | 风险 |
|---|---|---|
| 保留所有候选项 | 没有隐藏内容 | 模型看到歧义名称 |
| 最高优先级作用域获胜 | 调用简单 | 本地包可能遮蔽受信任的包 |
| 拒绝重复项 | 无静默遮蔽 | 合法的覆盖停止工作 |
| 按来源限定名称 | 显式身份 | 用户可见名称变得更长 |

为主机选择一个策略。即使它们不在模型目录中，也要在诊断中保留被拒绝或遮蔽的候选项。

### 三个披露层级

智能体技能规范描述了分阶段加载。关键点在于每个层级有不同的用途。

```figure
skill-disclosure-levels
```

#### 第一层：目录元数据

模型需要足够的信息来区分该技能与相邻技能。规范估计每个目录条目大约 100 个 token，但实际的序列化和 tokenization 属于主机。

有用的描述有两个子句：

```yaml
description: 验证发布候选版本并生成就绪报告。当用户询问版本、标签或软件包是否准备好发布时使用。
```

第一个子句陈述能力。第二个子句陈述触发边界。第 25 课使用正向和接近失败的提示评估此边界。

#### 第二层：活跃指令

激活后，主体应作为地图和程序运行。规范建议将 `SKILL.md` 保持在 500 行以下。这是一个设计信号，而不是要填满的目标。

主体应包含：

- 任务边界；
- 默认工作流；
- 分支条件；
- 对更深文件的直接引用；
- 工具和脚本契约；
- 失败和停止行为；
- 预期输出及其验证。

不要为了缩小入口文件而将核心工作流移入参考文件。激活必须为模型提供足够的上下文以正确开始。

#### 第三层：支持资源

参考提供文本或数据。脚本提供确定性计算。资产被复制、填充或转换为交付物，而不是作为指令处理。

| 目录 | 模型读取？ | 模型执行？ | 典型内容 |
|---|:---:|:---:|---|
| `references/` | 是，按需 | 否 | 模式、策略、领域指南 |
| `scripts/` | 可能检查 | 通过允许的工具 | 验证器、转换器、收集器 |
| `assets/` | 仅在有用时 | 否 | 模板、夹具、图像、起始文件 |

这些名称是约定，不是神奇的能力。主机仍然需要文件访问和执行工具。

### 分支特定引用优于主题转储

将入口文件写为决策地图：

```markdown
## 选择路径

- 对于 Python 包，读取 `references/python-release.md`。
- 对于容器镜像，读取 `references/container-release.md`。
- 对于纯文档发布，读取 `references/docs-release.md`。
- 如果发布结合多种工件类型，仅读取这些工件的指南。
```

这使每个引用都有可观察的加载条件。"读取 `references/` 以了解更多"则没有。

保持引用图浅层。官方指导建议从 `SKILL.md` 直接链接并避免深层链式结构。一跳使可达性可测试，并降低所需约束永远不进入上下文的可能性。

```figure
skill-reference-map
```

### 目录预算和活跃上下文是不同的预算

令 `c_i` 为技能 `i` 的序列化目录成本，`B_c` 为目录预算，`b_j` 为活跃主体成本，`r_k` 为实际加载的资源。

```text
catalog_cost = sum(c_i for every published skill)
active_cost = sum(b_j for every activated skill) + sum(r_k for every disclosed resource)
```

减少一个预算并不会自动减少另一个。简短描述可以节省目录空间，而激活的 900 行主体仍可能压倒任务。将主体拆分为参考只有在运行时和指令实际避免加载不相关分支时才能降低活跃成本。

Codex 目前在已知上下文窗口大小时，将初始技能列表预算为上下文窗口的 2%。8,000 字符值是当大小未知时的备用方案；它不是与 2% 规则组合使用的第二个上限。当目录超过适用预算时，描述可能被截断或省略。将这些数字视为当前 Codex 策略，而非智能体技能标准的属性。

### 资源路径是信任边界

技能应只读取其包内的文件。简单的字符串前缀检查是不够的：

```text
references/../../../../.ssh/config
references/external-link -> /private/company-secrets
```

解析包根和候选项，使用文件系统语义，拒绝绝对输入，并验证解析后的候选项是否仍在解析后的根目录下。在发现之前决定是否允许符号链接。如果允许，每次都检查解析后的目标。

```figure
skill-resource-containment
```

路径包容性不能建立内容信任。有效的包内引用仍可能包含恶意指令。第 26 课处理此威胁。

### 加载必须可观察

记录披露事件而不记录机密：

```json
{
  "event": "skill.resource.loaded",
  "skill": "release-readiness",
  "resource": "references/python-release.md",
  "reason": "候选项包含 pyproject.toml",
  "bytes": 2840
}
```

原因将上下文选择转化为可审查的证据。它还有助于识别导致智能体加载所有文件"以防万一"的指令。

## 构建

`code/main.py` 构建一个确定性的发现和披露引擎。

发现表面包括：

- 用于来源和优先级元数据的 `Scope`；
- 用于未验证文件系统候选项的 `SkillCandidate`；
- `discover_scope(scope)` 用于枚举即时技能目录；
- `resolve_collisions(candidates, precedence)` 用于应用已声明的策略；
- `CatalogEntry` 和 `build_catalog(...)` 用于发布有界元数据；
- `CatalogBudget` 用于统计序列化条目而不假装字符是通用 token。

披露表面包括：

- `load_skill_body(entry, ...)` 用于第一层激活；
- `validate_reference(skill_dir, reference)` 用于路径包容性验证；
- `load_reference(...)` 用于有界的第三层读取。

运行实验：

```bash
cd "$(git rev-parse --show-toplevel)"
cd phases/13-tools-and-protocols/24-skill-discovery-and-progressive-disclosure
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

此块需要本地克隆，并从该克隆内的任何工作目录解析仓库根目录。

演示创建临时项目和工作区作用域，插入冲突，在故意小的预算下构建目录，激活一个技能，并尝试有效的参考读取和穿越逃逸。不安装永久文件。

### 为什么发现是浅层的

`discover_scope` 检查即时子目录中的 `SKILL.md`。它不会递归地将每个嵌套的 `SKILL.md` 视为单独的包。这保留了包边界并避免意外发布已安装技能内部的示例或夹具。

### 为什么实验不解析任意 YAML

实验支持其目录所需的标量前导元数据。生产运行时应使用具有显式模式、大小限制和禁用自定义对象构造的安全 YAML 解析器。"仅限标准库"是一个教学约束，而不是默许发明部分 YAML 方言的许可。

## 使用

将此检查清单应用于任何发现适配器：

1. 列出所有配置根目录以及谁可以写入它们。
2. 声明是否允许符号链接包。
3. 验证包名称、目录名称、必需元数据和入口主体大小。
4. 在内部身份中保留来源和作用域。
5. 声明并测试重复名称行为。
6. 测量发送给模型的精确序列化目录。
7. 记录加载主体或资源的原因。
8. 将资源读取限制在解析后的包根目录内。
9. 在引用的文件缺失时明确失败。
10. 当安装或策略更改时重建目录。

## 交付

本课生成 `skill-catalog-builder` 包。它扫描显式排序的根目录，拒绝符号链接入口文件和名称-目录不匹配，解析跨作用域冲突，拒绝相同优先级的重复项，并将选定的元数据适配到声明的条目、描述和序列化字符预算中。

其 JSON 报告包含选定条目、遮蔽候选项、省略条目、验证错误、优先级和预算使用情况。主体和参考加载保持独立的运行时操作，因此目录构建器不执行脚本也不将整个包引入上下文。

## 练习

1. 添加一个插件作用域，并将其放在用户和内置优先级之间。用测试证明冲突结果。
2. 将冲突策略从最高优先级更改为限定名称。在目录中保留两个条目。
3. 向 `load_reference` 添加字节大小限制。测试恰好位于限制的文件和超出限制一个字节的文件。
4. 创建两个听起来几乎相同的描述。重写它们使触发边界不重叠。
5. 添加一个清单，包含每个参考和脚本的哈希值。在加载之前检测修改过的资源。
6. 为演示添加工具，分别报告第一层、第二层和第三层的字节计数。
